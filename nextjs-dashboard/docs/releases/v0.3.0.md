# v0.3.0 staging release

Release date: 2026-08-06

This release packages Phase 3 performance history and progress visualization
for the isolated staging environment. Public production deployment remains
deferred until the `v1.0.0` release review.

## Included changes

- Versioned performance calculation contracts.
- Filterable, paginated completed-workout history.
- Saved-timezone date boundaries and exercise filters.
- Snapshot-stable history summaries with English and Thai presentation.
- Exercise-detail history and personal-best presentation with canonical-unit
  calculations and equivalent metric/US displays.
- Weekly volume, peak estimated 1RM, completed-set active time, and consistency
  summaries with exercise and 4-to-26-week filters.
- Accessible charts with visible values and a keyboard-accessible equivalent
  table, including explicit empty weeks and bodyweight repetition reporting.

## Database and recovery

`20260805110000_performance_history.sql` adds a partial index on
`workout_session_exercises(exercise_id, session_id)`. It changes no rows and
does not alter RLS or grants.

`20260805130000_exercise_performance.sql` adds two security-invoker views for
completed exercise history and eligible personal-best sets. Existing table RLS
continues to enforce ownership; the views receive read-only authenticated
grants and do not alter workout records.

`20260805150000_performance_aggregates.sql` adds an authenticated,
security-invoker weekly-summary function. It reads owner-scoped completed
workouts through existing RLS, uses the saved timezone or UTC default, accepts
at most a 366-day range, and changes no workout rows.

`20260805152700_performance_weekly_summary.sql` replaces the weekly-summary
function without changing its signature. Duration now sums elapsed time from
completed sets on non-canceled exercises, avoiding inflation when a session is
left open across hours or days. It changes no workout rows.

For local rollback only, drop
`workout_session_exercises_exercise_session_idx` and the weekly-summary
function. For staging recovery, prefer another roll-forward migration that
recreates or replaces these objects after query-plan review.
